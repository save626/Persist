## 1. 项目是什么

Persist 是个人自用、本地优先的「计划 → 记录 → 复盘 → AI 分析」工具。

核心目标：

1. 在「今日」页统一安排与记录当天计划。
2. 记录健身、饮食饮水、学习与个人档案。
3. 把数据按日沉淀为历史。
4. 让 AI 只基于用户授权的真实数据写分析和建议。
5. 数据默认留在本机；只有用户显式开启同步后才上传增量副本。
6. 数据可导出、可备份、可恢复、可删除。

不能破坏的产品边界：

- 桌面网页第一期只有 demo / guest，不提供 owner 或真实 AI 入口。
- 完整产品只通过作者自有 Android APK 进入 owner。
- demo 的 AI 内容是部署前生成并固化的只读快照，部署后零 `/api/*`。
- guest 从空白开始，全部 AI 固定 Mock，零 `/api/*`。
- owner 才拥有真实 AI 和同步。

## 3. 三种运行模式

| 模式  | 入口                        | 数据                                     | AI                             | 同步   | 持久化               |
| ----- | --------------------------- | ---------------------------------------- | ------------------------------ | ------ | -------------------- |
| owner | 作者 Android 包默认进入     | 独立库 `persist-app`，首启为空白业务数据 | 真实 AI，失败时明确降级        | 可开启 | 是                   |

实现入口：

- 运行模式定义：`app/src/lib/runtime-mode.ts`
- 模式 Provider：`app/src/context/RuntimeModeProvider.tsx`
- 数据隔离：`app/src/context/MockDataProvider.tsx`
- web 构建：`npm --prefix app run build`
- mobile owner 构建：`npm --prefix app run build:mobile`

网页构建永远不能解析出 owner。`?mode=owner`、非法模式和无参数都按安全默认值处理：web 回落 guest，mobile 默认 owner。

## 4. 架构与数据边界

### 4.1 高层结构

```text
浏览器 / Android WebView
  ├─ React + Vite 单页应用
  ├─ 业务写入权威：IndexedDB
  ├─ owner 可选：增量同步 outbox
  └─ owner 可选：真实 AI 请求
          │
          ▼
Nginx :80
  ├─ /            落地页
  ├─ /home.html   产品介绍首页
  ├─ /app/        React web demo / guest
  └─ /api/*       → Fastify 127.0.0.1:3000
                       │
                       ├─ SQLite /var/lib/persist/persist.sqlite
                       ├─ 快照 /var/lib/persist/backups
                       └─ DeepSeek API
```

### 4.2 数据权威

- 业务记录的写入权威是当前设备的 IndexedDB。
- 服务端 SQLite 是用户显式开启同步后的可检索副本，不是本地写入权威。
- 同步副本不是备份；备份主体是服务端规范快照。
- 服务端 AI 综合分析只读同步上来的实体；未同步或未授权的数据不会进入事实包。
- 服务端分析归档不会自动回写本机，也不伪装成本地报告。

### 4.3 本地 schema 与服务端 schema

| 层            | 当前版本          | 说明                                                |
| ------------- | ----------------- | --------------------------------------------------- |
| App IndexedDB | `schemaVersion=3` | owner / guest 空白初始状态；v2 旧样例按精确指纹清理 |
| Server SQLite | schema `2`        | 同步实体、账号设备、分析归档与 job 表               |
| 导出格式      | `0.3.0`           | 可导入、兼容旧版本                                  |

### 4.4 同步语义

- 首次开启同步：`POST /api/v1/devices`，建账号和第一台设备。
- 第二设备：`POST /api/v1/devices/restore`，用固定恢复码换新设备令牌。
- 增量写入：`POST /api/v1/sync/push`，按 `opId` 幂等。
- 全量首次上传：`POST /api/v1/sync/bootstrap`，事务写入。
- 增量读取：`GET /api/v1/sync/pull?since=<rev>&limit=<n>`。
- 冲突策略：实体级 LWW，按客户端 `updatedAt` 后写胜。
- 删除策略：写墓碑并向其他设备传播。
- 服务端只存设备令牌和恢复码哈希，不存明文。

### 4.5 AI 数据边界

- owner 的 AI 请求必须满足：AI 总授权开启、对应来源开启、需要请求的数据存在。
- 三张观察卡：健身「训练观察」、饮食「今日观察」、学习「学习观察」调用真实 `/api/report`。
- 报告数字与指标由确定性代码计算；模型只写文字。
- 模型正文中的数字必须来自事实包；不合法时重试一次，仍不合法则报错，不编造归档。
- 无 Key、网络失败或上游失败时，允许明确降级为规则 / Mock，但不能伪装成真实 AI。

## 9. API 与账号数据闭环

### 9.1 路由分组

| 分组     | 路由                     | 鉴权                          |
| -------- | ------------------------ | ----------------------------- |
| health   | `GET /api/health`        | 无                            |
| AI 对话  | `POST /api/chat`         | 当前只有 IP 限流              |
| AI 报告  | `POST /api/report`       | 当前只有 IP 限流              |
| 设备     | `/api/v1/devices*`       | 注册 / 恢复无令牌；吊销需令牌 |
| 同步     | `/api/v1/sync/*`         | 设备令牌                      |
| 综合分析 | `/api/v1/analysis/*`     | 设备令牌                      |
| 报告归档 | `/api/v1/reports*`       | 设备令牌                      |
| 快照     | `/api/v1/backups*`       | 设备令牌                      |
| 导出     | `GET /api/v1/export`     | 设备令牌                      |
| 删除账号 | `DELETE /api/v1/account` | 设备令牌 + `confirm:true`     |

### 9.2 账号模型

- 一个账号 = 一个 `users` 行 + 多台 `devices`。
- 恢复码固定不变，32 位十六进制。
- 服务端只保存恢复码和设备令牌哈希。
- 令牌与恢复码只在创建响应中出现一次，响应使用 `no-store`。
- 恢复码可忽略空格、短横线和大小写。

### 9.3 删除账号规则

- 必须显式 `{ "confirm": true }`。
- 单事务删除业务行、分析归档、任务、同步台账、设备和账号。
- 成功后清理规范命名的快照及 `.sha256` 旁车。
- 若还有其他 active 账号且存在整库快照，返回 `409 account_delete_blocked`。
- 前端先删服务端，成功后再清本机；服务端失败不清本机。

### 9.4 2026-11-16 隔离账号测试

测试方式：

- 在生产机上使用已部署的 `/opt/persist-next/server/dist`。
- 启动隔离临时 Fastify 服务。
- 使用临时 SQLite 与临时备份目录。
- 结束后自动关闭服务并删除临时目录。

通过的 12 个检查点：

1. health
2. 未授权拦截
3. 注册
4. 初始 pull
5. push 幂等重放
6. 恢复码绑定第二设备
7. 跨设备 pull

9. 跨设备更新

11. 设备吊销
12. 删除账号与清理校验

结果：

## 11. 已知风险与限制

### 11.1 合规风险

- 生成式 AI 对外服务边界尚未正式闭环。
- 当前 IP 直连只适合内部调试。
- 前端模式隔离不能替代服务端鉴权。

### 11.2 数据风险

- 同步副本不是备份。
- 整库快照不能按账号裁剪；多账号同库时删除账号会被保护规则阻止。
- 恢复对象是整个 SQLite 文件，不是单账号恢复。
- 当前生产 3 组快照可能都对应空库；恢复前仍必须核验。

### 11.3 同步限制

- 冲突是实体级 LWW，不做字段级合并。
- 只同步本机已经落盘的记录。
- pull 的形状守卫会跳过旧客户端写坏的实体。
- 没有逐条冲突 / 失败 UI。
- 没有按切片暂停同步的开关。

### 11.4 AI 限制

- 无 Key 或上游失败时只能降级，不能保证真实 AI。
- 综合分析依赖同步副本；未同步时事实包为空。
- 数字由代码计算，模型只写文字；不要为了“更自然”放宽数字白名单。
- 每日简报默认关闭，并且读取同步上来的设置。

### 11.5 运维限制

- 2C2G 资源有限，不应在服务器构建前端。
- SQLite 使用 WAL，需要持续观察磁盘与锁。
- 当前 Node 内置 SQLite 仍会打印实验性警告，属预期。
