## 1. 项目是什么

个人自用、本地优先的「计划 → 记录 → 复盘 → AI 分析」工具。

1. 「今日」页统一安排与记录当天计划。
2. 健身、饮食饮水、学习与个人档案分模块记录。
3. 数据按日沉淀成历史台账。
4. AI 只基于用户授权的真实数据写分析，数字由确定性代码算。
5. 数据默认在本机；只有显式开启同步才上传增量副本。
6. 数据可导出、可备份、可恢复、可删除。

不可破坏的产品边界：桌面网页只有 demo / guest，真实 AI 只属于作者自有 Android owner 包；demo 的 AI 内容是部署前固化的只读快照；guest 全 Mock；两者都零 `/api/*`。

## 4. 架构与数据边界

### 4.1 高层结构

```text
浏览器 / Android WebView
  ├─ React + Vite 单页应用
  ├─ 业务写入权威：IndexedDB
  ├─ owner 可选：增量同步 outbox
  └─ owner 可选：真实 AI 请求（Authorization: Bearer psa_…）
          │
          ▼
Nginx :80
  ├─ /            落地页
  ├─ /home.html   产品介绍首页
  ├─ /app/        React web demo / guest
  └─ /api/*       → Fastify 127.0.0.1:3000
                       ├─ 凭据门 → IP 限流 → 日配额（次数 + token）
                       ├─ SQLite /var/lib/persist/persist.sqlite  (schema 3)
                       ├─ 快照 /var/lib/persist/backups
                       └─ DeepSeek API
```

### 4.2 数据权威

- 业务记录写入权威是本机 IndexedDB。
- 服务端 SQLite 是开启同步后的可检索副本，不是权威，**也不是备份**。
- 备份主体是服务端规范快照（`VACUUM INTO` + `.sha256` 旁车）。
- 服务端综合分析只读同步上来的实体；结果留在服务端归档，不回写本机。

### 4.3 schema

| 层            | 版本              | 说明                                                            |
| ------------- | ----------------- | --------------------------------------------------------------- |
| App IndexedDB | `schemaVersion=3` | owner / guest 空白初始状态；v2 旧样例按精确指纹清理             |
| Server SQLite | `3`               | v3 新增 `ai_usage`、`ai_calls`（P0 Step 2）；旧代码不读这两张表 |
| 导出格式      | `0.3.0`           | 可导入、兼容旧版本                                              |

### 4.4 AI 请求链路（P0 后的确定顺序）

```text
请求体校验 → Key 就绪检查 → 凭据门 → IP 限流 → 日配额（次数预占 + token 判余）→ 上游调用 → token 记账 + 审计落库
```

- 顺序不能随意调换：配额放在 IP 限流之后，避免脚本先刷光当日额度；凭据门在最前，未授权请求不消耗限流与额度。
- **次数**配额是「读→判→加一」的**单事务预占**，失败不退（宁可少放行，不可超发）。
- **token** 配额不能在生成前预知，所以是「进门判余 + 出门记账」：进门比对已记账量，出门累加本次实际用量。当天最后一次请求可以把总量顶过上限一截（最多一次请求的量）；被 abort 的流拿不到 usage，记 0（少算，不多算）。
- `/api/chat` 与 `/api/report` **共用同一份额度**——它们花的是同一个 Key 的钱。
- `gate=off` 时仍然计数（归到 `anonymous`），否则回滚门等于把止损一起关掉。
- 两维可独立关闭：`PERSIST_AI_DAILY_LIMIT=0` 只关次数，`PERSIST_AI_DAILY_TOKENS=0` 只关 token；两个都为 0 时连 `ai_usage` 都不写。

### 4.5 凭据形态与环境变量

| 变量                        | 含义                                                  | 生产当前值           |
| --------------------------- | ----------------------------------------------------- | -------------------- |
| `PERSIST_AI_KEYS`           | `k1:<sha256hex>[,k2:<sha256hex>]`，服务端只存哈希     | `k1:<64 hex>`        |
| `PERSIST_AI_GATE`           | `off` / `warn` / `enforce`                            | `enforce`            |
| `PERSIST_AI_DAILY_LIMIT`    | 每日请求上限，`0` 表示关闭这一维                      | `100`                |
| `PERSIST_AI_DAILY_TOKENS`   | 每日 token 上限（输入 + 输出），`0` 表示关闭这一维     | `200000`             |
| `PERSIST_AI_AUDIT_KEEP_DAYS` | `ai_calls` 保留天数，`0` 表示**不清理**（不是全删）    | `30`                 |
| `VITE_PERSIST_AI_KEY`       | 客户端明文 `psa_<32B base64url>`，**只允许**写在 `app/.env.mobile.local` | 已写入（不入库） |

约定：

- 客户端头固定 `Authorization: Bearer psa_…`；`pst_` 设备令牌一律判错。
- 四种失败形态（无头 / 错前缀 / 未知 keyId / 哈希不匹配）返回**完全一致**的 `401 ai_unauthorized`，不区分原因。
- 凭据表为空时 fail-closed（不是 fail-open）。
- 凭据只在 `build:mobile` 时内联；`vite.config.ts` 硬拦截：非 mobile 模式检测到该变量直接构建失败。
- 轮换必须**多 key 并行**：先加 `k2`，重打 APK，确认新包走通后再删 `k1`。不可直接覆盖 `k1`，否则旧包立刻 401。

### 4.6 前端失败语义

| 服务端返回              | 前端行为                                                     |
| ----------------------- | ------------------------------------------------------------ |
| `401 ai_unauthorized`   | 按既有「AI 不可用」语义回退本地规则 / Mock，并如实标注来源   |
| `429 ai_quota_exceeded` | 直接展示服务端 `error.message`（含上限与「明天 00:00 恢复」） |
| `5xx` / 超时            | 既有降级路径                                                 |

两个客户端本来就优先展示服务端 `error.message`，所以 Step 2 前端**零改动**，也没有触发视觉基线。

## 11. 已知风险与限制

### 11.1 安全

- 凭据是**静态 PSK 内联在 APK**：包被提取即可复用。当前靠「100 次/天 + IP 限流 + 可轮换」兜底，不是强身份。
- `k1` 明文只在 `app/.env.mobile.local`（gitignore），哈希在本机 `server/.env` 与生产 `/etc/persist/server.env`。轮换必须多 key 并行。
- CORS 只约束浏览器，从来不是鉴权；真正的门是 `PERSIST_AI_GATE`。
- `api/v1/*` 仍是设备令牌，没有用户密码体系（产品决定，不是缺陷）。

### 11.2 数据

- 同步副本不是备份；整库快照不能按账号裁剪，多账号同库时删除账号会被 409 保护挡住。
- 恢复对象是整个 SQLite 文件。
- 生产 7 份快照里，11-14/15/16 三份对应空库（11-17 才有真实数据），恢复前必须核验内容。
- `ai_calls` 现在只留 30 天：**30 天前的调用无法事后追查**。要长期留证就调大 `PERSIST_AI_AUDIT_KEEP_DAYS`，别在出事后才发现已经删了。

### 11.3 合规与发布

- 备案号未下发 ⇒ 不得用域名对外提供服务，不得宣称「已上线」。
- **生成式 AI 专门备案：本版决定不做（2026-11-17，用户决策）**。依据是一条可验证的事实链，不是「懒得办」：`app/src/lib/runtime-mode.ts` 的 `resolveRuntimeMode` 在 `surface: 'web'` 下**任何输入都不会返回 `owner`**（显式 `?mode=owner` 也回落 `guest`），`demo` / `guest` 的 `ai` 四项能力（`report` / `chat` / `morningBrief` / `serverAnalysis`）全为 `false` 且不请求 `/api/*`；真实 AI 只存在于 `npm run build:mobile` 产物，由作者本人在 debug APK 上使用。定性上属于**个人自用**，不构成「向境内公众提供生成式 AI 服务」。
- **但这是会被行为推翻的结论，不是一种状态**。以下任一发生，定性立即翻转、备案与安全评估回到硬门槛：把 owner 包给第二个人（发 APK、代装）、把 AI 凭据 `k1` 给别人、网页端以任何形式开放 owner 或真实 AI 入口、对外宣传「网页上能用 AI」。翻转前先改代码与文案，再谈合规——不要靠记忆守这条。
- 另一个**不是备案、但更近**的问题：当前 IP 直连 + cleartext，客户端把 AI 凭据放在 `authorization: Bearer` 头里明文发送，同网段可嗅探。只有作者一人使用时是可接受风险；一旦要给第二个人用，HTTPS 必须先于备案完成。

### 11.4 运维

- 2C2G，不在服务器构建前端。
- SQLite WAL，需持续观察磁盘与锁；当前磁盘 13.6%。
- Node 内置 SQLite 仍打印实验性警告，属预期。

### 11.5 本轮新增的诚实缺口

- ~~**配额路径尚未被真实请求验证**~~ **已关闭（17:00）**：真机 `/api/report` 200 → `ai_usage` `k1` 当日行 `requests=1 / prompt=772 / completion=349`，`ai_calls` `ok` 行同值、`latency_ms=2714`。**残留一半**：生产的这条是非流式路径（`completeJson`）；`/api/chat` 的 SSE `usage` 帧仍只有临时实例的证据（真实上游 975/77），下一次用 AI 建档对话时顺便确认一下。
- Step 1 的真机验证是在 `enforce` + Step 2 代码上线前完成的；Step 2 上线后只做了临时实例验证，没有再做一轮真机。
- 审计清理的删除逻辑已在**生产库**上验证（插标记行 → 删 → 复原），但「跑满 30 天之后的自然收敛」还没被时间验证过。
- **恢复演练的三条边界**（别把一次演练当成全覆盖）：① 演练的是「恢复到 12 秒前的快照」，不是「库损坏后从冷快照重建」——文件仍在同一目录、同一文件系统，跨盘 / 跨机恢复未验；② 恢复中途失败的**自动回滚**只有单测覆盖，生产上没有故意制造失败（那需要把库改坏）；③ 恢复是**整库替换**，当前单账号无影响，一旦出现第二个账号就会互相覆盖数据（`backup_user_mismatch` 只保证「快照含当前账号」，不保证「不动别人」）。
- **保留期是「收敛」不是「保证」**（P5-1）：设备水位只保证「墓碑产生之后那台设备联系过服务端一次」，不保证它把全部分页拉完了。所以一台超过 30 天没同步的设备回来后，已被清掉的墓碑对应的本地记录会残留成幽灵行——只能靠客户端重新 bootstrap 或手动删除，服务端已经没有信息告诉它「这条早删了」。同理，`sync_ops` 清掉后若客户端重放一个 30 天前的 op，会被当成新 op 再应用一次（结果幂等，但会多推一个 rev）。
- ~~**`audit_log` 只在生产库副本上验过写入**~~ **已关闭（18:08）**：真机吊销 + 恢复码重绑在生产落了 2 行（`device.revoke` / `device.restore` 均 `ok`），真实 HTTP → 中间件 → `recordAuditEvent` → 落库整条链路走通，`ip_hash` 复算与 `sha256(IP)[:16]` 一致。**残留部分**：七类动作里只真机走过 2 类，`account.delete` / `backup.*` / `export.read` 仍是副本验证——其中 `export.read` 更进一步：前端「导出 JSON」是纯本地 `Blob` 下载（文件名还带 `persist-mock-backup-`），根本不调 `GET /api/v1/export`，所以这条审计在 UI 上**不可达**，只有直接调 API 才会触发。
- **「关闭同步」不产生任何服务端痕迹**：`SyncEngine.disable()` 只改本地 `meta` 与定时器，不发请求。想让服务端知道「这台设备主动暂停了」得新加心跳字段，属于设计变更；本轮不做，代价是审计与 `devices.last_seen_at` 都无法区分「关了同步」与「关机了」。对墓碑清理无碍——设备水位停住只会让清理更保守。
- **`audit_log` 只记写动作，不记读**（除了导出）：`GET /reports`、`GET /backups` 这类高频读请求不进表，否则一天几百行全是噪声。代价是「谁在什么时候读过我的报告」这个问题答不了——想答需要另一张按需开启的访问日志，本轮不做。
- **分包后 E2E 出现过偶发**（P5-3）：第一次全量跑有 2 例失败（`day-rollover.spec.ts` 的饮食跨日、`mock-flows.spec.ts` 的 AI 来源证据），两例单独复跑都通过，第二次全量 132/132。没有定位到确定原因，最可能是分包后首屏多一次 chunk 请求、在 4 worker 并发下偶发慢于断言等待。**下次再遇到不要直接当 flaky 放过**：先看 `test-results/*/error-context.md` 的页面快照，确认是不是停在「正在载入…」占位上。
- **429 时同步徽标仍显示「已同步」**（P5-4 顺带发现）：`SyncState` 只按 `pending` 计算，不看 `error`。所以限流分支的文案说「已安排自动重试」、旁边徽标却说「已同步」，两者不一致。属既有行为，未在本轮改动（改 state 计算会牵动全部同步状态的基线）。
- 演练暴露的属主缺陷说明：`backup-cli.js` 以 root 跑出来的快照，服务进程读不了 `.sha256`，而 `GET /api/v1/backups` 对这种情况只返回 `sha256: null`、**不会报错**——列表看着正常，恢复时才失败。已修属主并在部署文档立规矩。
