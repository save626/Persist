## 0. 一分钟读完

Persist 是一个**个人自用、本地优先**的「计划 → 记录 → 复盘 → AI 分析」工具：不做游戏化打卡，不制造全勤压力，只帮一个人看清自己在健身、饮食、学习上的真实长期轨迹。

```text
建立个人档案 → 制定今日计划 → 健身 / 饮食饮水 / 学习记录
      → 晚间复盘 → AI 生成分析文字 → 看周期趋势 → 调整档案与下一阶段计划
```

**现状（2026-11-05）**：前端八个页面全部可用并通过桌面端 + 移动端视觉验收，**前端已冻结**（唯一例外：经用户批准的今日页晨间简报接入真实 AI）；业务数据写入本机 IndexedDB（刷新 / 关标签页 / 重开浏览器不丢），步骤 11（8d）起训练 / 饮食 / 饮水 / 计划按日台账落历史（`schemaVersion` 2），备份升级为 0.3.0 并兼容 0.2.0 / 0.1.0；AI 建档、报告文字与晨间简报文字在「档案页开启授权 + 服务端可用」时经自建代理调用真实 DeepSeek，失败自动回退本地 Mock 并如实标注来源。**服务端已于 2026-11-04 以 IP 直连方式部署（Nginx + systemd），仅内部调试，未宣称上线**。

**下一步**：P4 的步骤 12（账号 + 增量同步，12a–12f）已于 2026-11-05 **在本机完成并验收、未部署、未推送**（服务端 SQLite 数据层与 `/api/v1/*`、`@persist/shared` 同步契约、客户端同步层、设置页「数据同步」卡片；app 单测 292/292、server 112/112、E2E 110、P4 §7.4 验收 19/19）。**部署依赖步骤 10 把服务器升到 Node ≥ 22.5**（`node:sqlite`）。接下来可按备案进度二选一：等备案号做步骤 10（域名 + HTTPS + 前端产物部署 + Node 22 + 部署步骤 12），或在本地推进步骤 13（AI 综合分析：跨模块事实包 → 单次调用 → 只写文字）。对外上线仍等备案号下发。

**三条硬约束**（任何阶段都不能破）：

1. **本地优先**：核心写入先落本机，服务器挂了 / 断网 / 没 Key 都必须能继续用。
2. **诚实**：Mock 不伪装成 AI；计划不写成现状；未授权模块对 AI 不可见；不得宣称「已上线」，不得编造备案号。
3. **一次一步**：每步做完写报告、停下等确认，不连做、不擅自扩大范围。

## 1. 项目背景与产品目标

### 1.1 愿景

Persist 是一个安静、可信、可持续的个人数据面板：

- 能快速记录一天中真正重要的信息（10 秒内完成一次记录）。
- 能把分散在健身、饮食、饮水、学习里的记录联系起来，而不是四个互不相干的计数器。
- 能通过 AI 给出**有上下文**的分析（数据来自自己的历史），而不是泛泛的鼓励话。
- 能看清长期趋势，不被单日波动干扰。
- **数据首先属于用户**：默认保存在本机，可随时导出、可彻底删除。

### 1.2 要解决的问题

1. 记录分散在多个 App，数据互不相通，无法形成「一天」的整体视图。
2. 打卡类工具用连续天数制造压力，一旦中断就放弃。
3. 通用 AI 不知道自己昨天吃了什么、练了什么，分析只能靠用户口述。
4. 手写表格 / 备忘录难以积累，也无法统计。
5. 数据托管在第三方服务里，导出困难、随时可能消失。

### 1.3 第一版成功标准（现状对照）

| 标准 | 状态 |
|---|---|
| 8 个页面全部可用，桌面端 + 移动端视觉统一 | ✅ 已验收（15 状态 × 6 视口基线） |
| 一天闭环可完整走通：计划 → 记录 → 指标聚合 → 复盘 / 报告 | ✅ 已可用（指标为本地确定性聚合） |
| 刷新 / 重开浏览器 / 清进程后数据不丢 | ✅ 本机 IndexedDB 持久化 |
| 无网络、无 Key、未授权时仍可正常记录 | ✅ 自动回退 Mock 并标注来源 |

## 2. 已确认决策与项目边界

### 2.1 已确认决策（含对规划的偏离）

| 项目 | 决策 |
|---|---|
| 产品名称 / 定位 | Persist / 个人自用计划、记录、统计与 AI 复盘工具 |
| 主要使用平台 | 手机浏览器（后续 Capacitor 打包 Android），开发与验收在桌面 Chrome / Edge |
| 一级导航 | **五项**：今日、健身、饮食、学习、AI 报告（旧规划为四项，AI 报告为辅助页——已偏离并确认） |
| 辅助页面 | 个人档案（`/profile`）、设置（`/settings`）、长期计划（`/plans`），不进主导航 |
| 学习范围 | 英语 + 高数，第一版只做手动统计 |
| 英语背诵 | 在外部 App 完成，Persist 只记录结果与时长 |

| 数据策略 | **本地优先**：IndexedDB 为唯一读写源（原生实现，非 Dexie）；服务端 SQLite 是「可检索副本」，不是主库 |
| 服务器 | 阿里云 ECS 2C2G，承担 AI 代理，后续承担同步 / 报告缓存 / 备份 |
| Android 打包 | Capacitor + Gradle，USB 安装 APK |
| UI 设计方式 | 不用 Figma；HTML 原型由 Agent 产出、用户评审确认后手写 CSS 落地 |
| 视觉基调 | 灰白 + 低饱和浅蓝，已由用户确认（色值与字号见工程约定 §2） |
| 开发顺序 | 先把全部页面视觉与交互做完并验收冻结，再推服务端与数据层 |

### 2.3 第一版明确不做

- 不抓取「不背单词」「百词斩」等外部 App 的非公开数据。
- 不做单词书自动拆解与艾宾浩斯排程。
- 不做饮食照片识别、食物数据库、条码扫描。
- 不提供医学诊断、疾病治疗或极端减脂建议。
- 不做社交、排行榜、连续打卡惩罚、积分与勋章。
- 不做多用户、家庭共享、公开主页。
- 不做首版多设备实时双向同步（只做「本地优先 + 增量副本」）。
- 不接入智能手表、体脂秤、Health Connect。
- 不做开放式聊天机器人；AI 只产出结构化场景文字，不直接写数据。

### 2.4 后续候选能力（未排期）

- 单词书 CSV / JSON 导入与每日计划拆分。
- 饮食照片识别、食物库、条码扫描。
- 训练模板 / 复合动作模板、周期化训练计划、伤病保护提示。
- Health Connect、体脂秤、手表接入。
- 月度 / 季度趋势报告与更细的 AI 建议。
- 报告定时生成（每日 21:00）与归档（已在 P4 设计中预留）。
- 多设备冲突解决界面、分享只读摘要。

## 3. 用户与使用场景

### 3.1 目标用户

**单一用户，就是作者本人**。这决定了三件事：不做账号体系（P4 用设备令牌 + 恢复码）、不做多语言（仅中文）、不做运营功能。也决定了产品取舍的第一原则是「自己明天还愿不愿意打开它」。

### 3.2 一天里的四个使用时刻

| 时刻 | 场景 | 产品回应 |
|---|---|---|
| 早晨 | 看今天要做什么、还剩几天到目标 | 今日页计划 + 双倒计时 + （授权后）晨间简报 |
| 白天 | 健身后、吃饭时、学习结束时随手记一笔 | 三个模块的快速记录入口，不强制填全 |
| 晚间 | 回头看看今天完成度，写两句复盘 | 今日指标聚合 + 报告页生成复盘 |
| 周期性 | 想知道这两周在变好还是变差 | 报告页 / 后续的趋势视图（需 P4 历史检索） |

### 3.3 设备与网络假设

- 主用手机浏览器；电脑上也能看。窄屏 360 px 起，桌面到 1440 px。
- 假设网络**经常不可用**：地铁、健身房、断网时都必须能记录。
- 服务端可能挂、Key 可能过期：这些都是常态而非异常，UI 必须优雅降级。
- 单人单设备为主，未来可能换手机 / 多设备 ⇒ 需要备份与增量同步（P4）。

### 3.4 成功信号

- 连续使用两周后，仍愿意每天记录 ≥3 条。
- 报告里的数字能对上自己记得的事（不出现「模型自己算的数」）。
- 换设备 / 重装后数据能回来（P4 之后）。

## 4. 信息架构与页面地图

### 4.1 页面清单（8 个）

| 路径 | 层级 | 职责 | 现状 |
|---|---|---|---|
| `/` | 一级（今日） | 计划、四项指标、双倒计时、时间线、快速记录 | ✅ |
| `/fitness` | 一级（健身） | 今日训练、动作与组数、自由运动、历史与趋势 | ✅（历史仍为演示常量，见步骤 11） |

| `/study` | 一级（学习） | 英语 / 高数会话记录与统计 | ✅（唯一自带 `date` 的模块） |
| `/reports` | 一级（AI 报告） | 指标、依据、生成简报 / 复盘 / 周报，标注来源 | ✅（指标本地生成，文字可走模型） |
| `/profile` | 二级（个人档案） | 基本信息、目标、AI 授权开关、AI 引导建档 | ✅ |
| `/plans` | 二级（长期计划） | 草案 → 启用 → 归档，起止日期可编辑 | ✅ |
| `/settings` | 二级（设置） | 数据源开关、导出 / 导入、清空本机数据、AI 状态 | ✅ |

### 4.2 跨页联动（不能各自为政）

1. 健身 / 饮食 / 学习写入 → 今日四项指标立即变化。
2. 今日计划项完成 → 计划完成率与时间线同步。
3. 档案页 AI 建档 → 产出长期计划草案 → 启用后进入 `/plans`，并影响今日计划区。
4. 报告页读取各模块摘要 → 生成文字时只带**已授权**的模块。
5. 设置页清空 / 导入 → 所有页面回到初始或新数据，不能残留旧引用。

### 4.3 路由与深链约定

- SPA + `BrowserRouter`，Nginx 必须 `try_files $uri /index.html`，且 `/api/` 的 location 要**排在静态回退之前**。
- `/plans` 必须支持直接输入地址访问（部署验收项之一）。
- 报告 / 分析类页面不依赖服务端渲染，深链刷新必须可用。

### 4.4 已废弃的旧信息架构（不要恢复）

旧规划里的「四项一级导航」「AI 报告为学习页附属」「16 条建议路由」「独立的备份页 / 同步页 / 统计页」都**不是现状**，也不在计划内。旧的 `docs/Persist-项目开发规划.md` v1.2 原文可从 `git show fccce42:docs/Persist-项目开发规划.md` 取回，仅作历史参考。

## 5. 功能规划（按模块）

> 每个模块写三件事：**目标**（要做到什么）、**现状**（已实现什么，细节见 `HANDOFF.md` §4）、**后续计划**（哪一步做）。

### 5.1 今日

- **目标**：一天的控制台。打开就知道要做几件事、完成到哪、喝了多少水、学了多久、离两个目标还有几天。
- **现状**：计划增删改排序完成、四项指标聚合、双倒计时（可配置、持久化、到期态）、时间线、快速记录入口；结束今日并填写状态的路径已通。
- **后续**：步骤 11 让「今日」不只是今天（按日台账）；步骤 13 让指标来自真正的历史聚合。

### 5.2 健身

- **目标**：记录一次训练的最小成本方式——动作、组数、次数、重量（或时长），并能看出这周练了几次、练了什么。
- **现状**：今日训练可增删动作与组、自由运动（有氧 / 时长）可记、基础统计可用；**历史列表仍是页面内演示常量**，不是真实台账。
- **后续**：步骤 11 把训练会话落成带日期的真实记录（结构通用化，力量 / 有氧统一），并重跑视觉基线；步骤 13 让 AI 能聊训练量趋势。

### 5.3 饮食与饮水

- **目标**：餐次、热量、三大营养素手填；饮水一键加一杯；两边都有 7 天趋势。
- **现状**：餐次增删、热量与宏量营养素手填、饮水 125 / 250 / 自定义 / 撤销删除、目标与趋势视图都可用；照片只存文件名；**只有今天的 `meals`，饮水记录无日期**。

## 6. 数据与技术架构

### 6.1 现状（已实现）

| 层 | 现状 |
|---|---|
| 前端 | React 19 + TypeScript + Vite（Rolldown）+ React Router；手写 CSS（`app/src/styles/home-v3.css` 为主）；Tailwind 在依赖里但**未用于已验收视觉**；Oxlint + Prettier 管风格 |
| 本机存储 | **原生 IndexedDB**：库 `persist-app`，单对象仓库 `mock-state`，单记录键 `record:persist-mock-state`；13 个数据切片一次提交；每次写入 100–300 KB，200 ms 防抖；`MIGRATIONS` 表负责 v0 → v1；异常分 `unsupported-version` / `unavailable`（2 s 超时）/ `corrupt` 三态 |
| 服务端 | Fastify 5，ESM + NodeNext，`GET /api/health`、`POST /api/chat`（SSE）、`POST /api/report`（JSON）；步骤 12 起加 `/api/v1/devices*`、`/api/v1/sync/*`（**未部署**）；请求体上限 256 KB；按 IP 限流 20 次 / 300 s（chat 与 report 共用；`/api/v1/*` 独立 240 次 / 300 s）；日志脱敏；Key 仅在服务器 `/etc/persist/server.env`（600 权限） |
| 部署形态 | 前端构建成纯静态由 Nginx 托管（`/var/www/persist`）；Fastify 只监听 `127.0.0.1:3000`，由 Nginx 反代 `/api/*`；systemd 守护（`persist-server.service`） |
| 备份 | JSON 0.3.0（含长期计划与按日历史，兼容 0.2.0 / 0.1.0）；导入为整体替换、不可撤销 |

**为什么不做多 store / 不做增量写**：单人自用、数据量在 MB 级，单记录整体提交换来「一次写入即一致」的简单性；等 P4 引入按日台账与同步时再拆分（届时 `schemaVersion` 升到 2）——**该拆分已于步骤 11（`schemaVersion: 2` 按日台账）与步骤 12（`persist-sync` outbox）落地，主记录仍保持单记录整体提交**。

### 6.2 终态：本地优先 + 服务端可检索副本（P4；步骤 12 已落地本地优先 + 增量同步，服务端聚合分析待步骤 13）

- **本地仍是主库**：没有服务端时产品功能完整，与今天一致。
- **服务端 SQLite 是可检索副本**：只存聚合与检索所需的结构化数据，让 AI 能查历史、出跨月报告。
- **增量同步**：本地 outbox 队列，`opId` 幂等；`updatedAt` 做 LWW；服务端 `sync_seq` 提供单调 `rev` 作游标；墓碑保留 30 天支持删除同步。
- **鉴权**：单用户设备令牌 + 恢复码（不做注册登录，不做多用户）。
- **AI 只写文字**：服务端 SQL 聚合 → 事实包 `ReportFacts` v2 → DeepSeek 只把事实写成中文；模型不参与算术，也不直接写库。
- **报告生命周期**：缓存 / 归档 / 可选每日 21:00 定时生成；模型不可用时规则引擎兜底并标注。

设计细节（表结构、DDL、同步协议、事实包字段）全在 [`P4-数据层与AI综合分析设计方案.md`](P4-数据层与AI综合分析设计方案.md)，本文件不重复。

### 6.3 技术选型偏离（重要，不要照旧规划实施）

| 旧规划写法 | 现状 / 计划 | 原因 |
|---|---|---|
| Dexie（IndexedDB 封装） | **不用**，直接用原生 IndexedDB | 单记录读写简单，省一层依赖与升级风险 |
| ORM（Drizzle 等） | **不用**，SQLite 直写 SQL | 表少、SQL 简单，省构建与版本耦合 |
| Docker Compose 部署 | **不用**，systemd + Nginx | 2C2G 单机，容器只会增加内存与运维成本 |
| MySQL | **不用**，单文件 SQLite | 单人单写，备份 = 拷一个文件 |
| 前后端独立仓库 / monorepo 工具链 | 单仓库三目录（`app` / `server` / `shared`） | 规模不需要 turbo / nx |

**SQLite 驱动已拍板（2026-11-05）**：选**方案 A**——服务器在步骤 10 一并升级到 Node ≥ 22.5，用内置 `node:sqlite`（无 native 编译依赖，CentOS 系不需要额外工具链）；`server/package.json` 的 `engines` 已写 `>=22.5`。驱动差异仍全部隔离在 `server/src/db/driver.ts` 单文件里，若将来要回退方案 B（`better-sqlite3`）只改这一个文件。决策记录见 `docs/P4-数据层与AI综合分析设计方案.md` §11.4。

## 8. AI 能力规划

### 8.1 现状（8b / 8c 已完成）

- **两条独立链路**：`/api/chat`（建档对话，SSE 流式）与 `/api/report`（报告文字，非流式 JSON）。
- **授权门控**：档案页 `aiConsent` + 设置页数据源开关，决定哪些模块的摘要会被发送；未授权模块在摘要里是 `null`，模型看不到。
- **能力探测**：前端先探 `/api/health`，`ai:"deepseek"` 才走真实链路，否则直接用 Mock。
- **来源标注**：每段 AI 文字都带 `origin: 'ai' | 'mock'`，界面如实显示，Mock 绝不伪装成真实分析。
- **失败回退**：超时 / 网络错误 / 契约错误 / 服务不可用 → 自动回退并在界面说明原因。

### 8.2 目标链路（步骤 12–13）

```text
本机记录 --同步--> 服务端 SQLite --SQL 聚合--> ReportFacts v2 --提示词--> DeepSeek 写中文
                                                              └──> 规则引擎兜底（不可用时）
报告 -> 缓存 / 归档 -> 前端展示（含生成时间、范围、来源标注）
```

关键原则：**数字与事实由 SQL 与确定性代码产生，模型只负责组织语言**；模型输出即使异常，也不能影响指标正确性。

### 8.3 隐私边界（PIPL 视角）

- 只发送用户已授权的模块摘要；授权可随时关闭，关闭后立即生效（下一次请求不再携带）。
- 请求体、个人档案、完整提示词**不进日志**；服务端日志只记状态码、耗时、错误类型。
- Key 只在服务器，浏览器永远拿不到；仓库、构建产物、日志里不得出现 `sk-`。
- 提供导出与删除路径：本机清空（已有）、服务端删除账号与数据（步骤 14）。
- 保留期默认设想 365 天（报告）/ 30 天（墓碑）/ 30 天（审计），仍待确认（见 §14）。

### 8.4 降级与成本控制

- 无 Key / 未授权 / 服务挂 → 本地 Mock 或规则文案，界面标注，功能不中断。
- 限流 20 次 / 300 s（按 IP），防误点与滥用；2C2G + 3 Mbps 按流量计费的机器不能承受大流量。
- 报告请求 25 s 超时（Nginx 侧 `proxy_read_timeout ≥ 60 s`），避免长连接堆积。
- 上线前**必须轮换**开发期用过的 Key；更换 Key 只改 `/etc/persist/server.env` 并重启服务。
- 成本预期：单人日常使用下 token 消耗很小，量级在「每月几元」，不需要预付费包（实际以账单为准，不写死金额）。

### 8.5 提示词纪律（真实联调踩过的坑）

1. 禁止模型做任何算术：出现过「1.5 − 1.0 推出再补水 0.5 L」这种凭空数字。
2. 注入 Asia/Shanghai 的「今天」，否则模型会写出过去日期。
3. 只允许使用给定事实包里的字段，不得编造记录、不得写医学结论。
4. 输出结构固定（段落 / 固定小节），前端按结构渲染，不做自由 HTML。
5. 每次改了提示词都要用真实 Key 复验一次，并检查「是否出现新数字」「是否出现过去日期」。

### 8.6 AI 明确不做

- 不做开放聊天（只有建档对话与报告两类场景）。
- AI 不能直接写入任何记录或计划；需要用户确认才落地（P4 结构化建议实现后同样适用）。
- 不做医学诊断、疾病治疗、极端减脂建议。
- **在步骤 13 完成前，不得宣称「AI 能分析历史 / 能出跨月报告」。**

### 11.2 测试纪律（容易踩的坑）

- Playwright 必须 `channel: 'chrome'`（内置 chromium 在本机不可用）。
- **E2E 不得打到真实后端**：脚本强制 `PERSIST_API_TARGET=http://127.0.0.1:9`，用不可达端口保证 AI 链路走 Mock。
- `visual:check` 需要一个**没有 Key 的后端**在跑（`cd server && node dist/index.js`），否则截图会因真实 AI 文案而漂移。
- 截图浏览器在受限沙箱下无法启动，需要一次性放宽权限；这是环境限制，不是测试失败。
- 基线数字变化必须在报告里解释原因（新增用例、删用例、文案变化），不能悄悄改。

### 11.3 诚实性检查（本项目的特殊要求）

- 每段 AI 文字必须有 `origin` 标注；E2E 断言 Mock 状态下界面显示「本地 Mock」。
- 契约错误必须显式报错，不能静默降级成 Mock（否则用户会以为数据出了问题）。
- 报告里的数字必须能在本地记录里找到对应来源；「依据」条目不能由模型生成。
- 未授权模块不得出现在请求体里（单测断言 `digest: null`）。

## 附录 B：术语

- **今日闭环**：计划 → 记录 → 指标聚合 → 复盘 / 报告，形成完整一天。
- **本地优先**：核心写入先落本机，服务器不可用不影响使用。
- **事实包（`ReportFacts`）**：服务端聚合出的结构化事实，模型的唯一输入来源。
- **确定性指标**：由本地记录直接算出的数字，不经模型。
- **来源标注**：`origin: 'ai' | 'mock'`，界面如实显示文字来自哪里。
- **确认式修改**：AI 不能直接写数据，必须用户确认才落地。
- **软删除 / 墓碑**：记录保留删除标记（设计保留 30 天，用于撤销与同步；清理任务尚未实现）。
- **Outbox**：本地待同步操作队列，保证断网时的写入不丢。
- **视觉 Token**：颜色、字号、间距、圆角等统一设计变量。
