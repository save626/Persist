## 0. 文档摘要

Persist 是一款面向个人长期使用的计划、记录与复盘工具。它不做游戏化打卡，也不以“全勤”制造压力，而是帮助使用者形成稳定的日常闭环：

```text
建立个人档案
→ 制定今日计划
→ 在健身、饮食饮水、学习中记录
→ 晚间复盘
→ AI 综合分析与建议
→ 查看周期趋势
→ 调整个人档案和下一阶段计划
```

第一版规划包含四个业务入口（AI 报告作为独立入口的来源见下方现状说明）：

```text
今日 / 健身 / 饮食 / 学习
```

其中：

- “今日”负责一天的计划、进度、时间线、AI 晨间简报与晚间复盘。
- “健身”负责训练计划、动作和组数记录、训练统计。
- “饮食”同时包含饮食和饮水，负责餐次、热量、宏量营养素、饮水量和趋势。
- “学习”统一记录英语与高数，第一版只做统计记录，不做单词书自动排程。
- “个人档案”“AI 报告”“设置”作为辅助页面，不进入主导航。

> 现状偏差（2026-11-02）：实际实现中 **AI 报告已成为第五项一级导航**，理由是报告是本产品的主出口而不是学习页附属功能；“个人档案”“设置”仍为二级页面。另外 `/plans` 长期计划页为二级页面，可从档案页 AI 建档、今日页计划区与深链进入。详见 `HANDOFF.md` §3。

第一版的核心判断标准不是功能数量，而是能否真实支撑每天从计划到复盘的完整闭环。

## 1. 项目背景与产品目标

### 1.1 产品愿景

Persist 是一个安静、可信、可持续的个人数据面板：

- 能快速记录一天中真正重要的信息。
- 能把分散在健身、饮食、饮水、学习中的记录联系起来。
- 能通过 AI 给出有上下文的分析，而不是泛泛而谈。
- 能让用户看清长期趋势，而不是被短期波动影响。
- 数据首先属于用户，默认保存在本地，并支持导出与备份。

### 1.2 核心问题

当前工具需要解决以下问题：

1. 健身、饮食、饮水和学习数据分散在不同 App 中，难以综合分析。
2. 普通打卡工具强调连续天数，容易带来压力，不能真实反映状态。
3. 饮食照片识别和食物数据库会显著提高第一版复杂度，但仍需保留记录入口。
4. 英语背诵主要发生在“不背单词”“百词斩”等外部 App，本工具不应重复实现背诵功能。
5. AI 建议若不结合个人档案和历史数据，容易停留在泛泛而谈。
6. 手机端与电脑端需要共享同一套界面逻辑，最终通过数据线安装 Android APK。

### 1.3 产品原则

- **记录优先**：AI 不可用、服务器不可用时，所有记录功能必须正常工作。
- **低摩擦**：饮水、学习、训练等高频操作应尽量在 1～3 次点击内完成。
- **长期主义**：使用趋势、阶段平均和上下文解释，不设置惩罚式连续打卡。
- **用户掌控**：AI 只能建议，不能静默修改计划、目标或档案。
- **隐私最小化**：只向 AI 发送当前分析所需的数据，API Key 不进入客户端安装包。
- **可解释**：AI 结论要标明依据的时间范围、记录数量和不确定性。
- **渐进扩展**：先完成稳定闭环，再增加照片识别、词书排程和复杂同步。

### 1.4 第一版成功标准

第一版发布时，应满足：

- 用户可完成 AI 引导式个人建档，并随时修改。
- 用户可创建、调整和完成今日计划。
- 健身训练、饮食热量、饮水和学习均可离线记录。
- 关闭并重新打开应用后，记录仍然存在。
- 一天结束后可填写状态并生成 AI 晚间复盘。
- 可查看近 7 天和基础月度统计。
- 可导出完整数据并在空数据库中恢复。
- Android APK 可安装到目标手机，桌面浏览器可完成主要操作。
- DeepSeek 不可用时，页面能提示失败，不影响已有记录和后续补录。

| Android 打包 | Capacitor + Android Studio / Gradle，通过 USB 部署 APK |
| UI 设计方式 | 不使用 Figma，由 Agent 通过 HTML 原型设计并由用户评审 |
| 视觉基调 | 灰白 + 低饱和浅蓝，已由用户确认 |
| 设计参考 | Superdesign Skill 已安装；HTML 原型是当前视觉基线 |
| 开发顺序 | 先完成全部核心页面的视觉统一与用户验收，再推进服务端后端功能 |

### 2.2 第一版必须实现（MVP）

- 今日计划与完成状态。
- 今日四项聚合指标：计划完成、饮食热量、饮水量、学习时长。
- 今日双倒计时：两个自定义重要目标。
- 今日时间线和快速记录入口。
- 健身计划、训练记录、动作明细和基础趋势。
- 饮食餐次、热量、蛋白质/碳水/脂肪的手动记录。
- 饮水快捷增加、半杯/一杯、自定义量、删除与撤销。
- 学习记录：英语/高数分类、来源、时长、数量和备注。
- 一次学习会话对应一条学习记录，便于按每次学习进行统计。
- 个人档案与首次使用引导。
- AI 晨间简报、晚间复盘、基础周报。
- 本地持久化、JSON 导出/导入。
- DeepSeek 服务端代理及密钥保护。
- 桌面响应式界面与 Android 安装包。

### 2.3 第一版明确不做

- 不抓取“不背单词”“百词斩”等外部 App 的非公开数据。
- 不在第一版实现单词书自动拆解和艾宾浩斯排程。
- 不做饮食照片自动识别或食物数据库搜索。
- 不提供医学诊断、疾病治疗或极端减脂建议。
- 不做社交、排行榜、连续打卡惩罚、积分和勋章。
- 不做多用户、家庭共享或公开主页。
- 不追求首版多设备实时双向同步。
- 不接入智能手表、体脂秤或 Health Connect。
- 不做复杂聊天式 AI，仅提供结构化分析与追问。

### 2.4 后续候选能力

- 单词书 CSV / Excel / JSON 导入与每日计划拆分。
- 饮食照片识别、食物数据库和条码扫描。
- 多设备增量同步与冲突解决界面。
- 训练模板市场或用户自定义复合模板。
- Health Connect、体脂秤、智能手表数据接入。
- 月度、季度趋势报告和更细致的 AI 建议。
- 周期化训练计划、伤病保护和恢复建议。

## 3. 用户与使用场景

### 3.1 用户画像

- 单一使用者：项目所有者本人。
- 希望通过一个工具综合查看身体、饮食和学习状态。
- 愿意手动录入或从其他 AI 工具复制热量结果。
- 需要快速记录，但不希望被复杂表单打断。
- 重视隐私、数据可导出和长期可维护性。

### 3.2 设备与界面

- Android 手机：主要使用场景，采用底部导航、单列卡片、快捷悬浮按钮。
- 桌面浏览器：开发、检查和长时间整理数据。
- 手机屏幕适配目标：360px～430px 宽度无横向滚动。
- 桌面适配目标：1280px～1600px 宽度下侧栏主导航、双列内容。
- 不单独开发 iOS 版本，但前端实现不应依赖 Android 专属 API。

### 3.3 典型使用流程

#### 首次使用

1. 用户打开应用。
2. 进入个人档案引导。
3. 填写基础信息、目标、作息、训练与饮食约束、学习目标。
4. AI 通过少量追问补全档案，并生成结构化草稿。
5. 用户确认或修改后保存。
6. 系统引导用户创建第一份今日计划。

#### 每天开始

1. 用户打开“今日”。
2. 查看 AI 晨间简报与昨日趋势。
3. 接受、调整或自行添加今日安排。
4. 从计划项进入对应记录页面。

#### 日常记录

- 健身：从今日计划或健身页开始一次训练，记录动作、组数、次数、重量和时长。
- 饮食：记录餐次与热量；可附照片和备注；营养数据由用户手动填写。
- 饮水：点击一次增加 250ml，也支持半杯、自定义和撤销。
- 学习：点击一次记录学习会话，选择英语/高数、来源和完成数量。

#### 每天晚上

1. 用户点击“结束今日”。
2. 填写精力、情绪、睡眠、酸痛、饮食状态和自由备注。
3. AI 结合档案、计划、记录和状态生成复盘。
4. 用户可保存结论、生成明日建议或要求重新分析。
5. AI 建议必须由用户确认后才能写入明日计划。

## 5. 功能规格

### 5.1 今日

#### 5.1.1 今日头部

显示：

- 日期、星期和一天状态。
- 简短中性文案，不使用强刺激口号。
- “编辑计划”入口。
- “快速记录”入口。
- 当前日状态：未开始、进行中、待复盘、已结束。

#### 5.1.2 今日指标

四项指标：

1. 计划完成：已完成数 / 计划总数。
2. 饮食摄入：总热量 / 目标热量。
3. 饮水：已饮用量 / 目标量。
4. 学习：总学习分钟 / 目标分钟。

行为：

- 点击指标进入对应模块的当日详情。
- 数据来自实时聚合，不另存冗余总数。
- 目标为空时显示“未设置目标”并提供设置入口。

#### 5.1.3 今日安排

计划项字段：

- 所属模块：健身、饮食、学习、其他。
- 标题。
- 计划时间或时段。
- 预计时长。
- 关联记录类型。
- 完成状态：待完成、进行中、已完成、跳过。
- 跳过原因。
- 备注。

行为：

- 用户可拖动排序或通过“调整”进入排序模式。
- 勾选完成只修改计划项状态，不自动伪造记录。
- 从计划项点“开始”可创建对应记录草稿。
- AI 生成的计划项带来源标识，仍需用户确认后保存。

#### 5.1.4 最近记录时间线

按时间倒序显示：

- 饮水记录。
- 餐次记录。
- 训练记录。
- 学习记录。
- 用户手动补充的其他事件。

要求：

- 每条记录可进入详情。
- 高频记录支持删除并撤销。
- 记录数量较多时分页或按时间段折叠。

#### 5.1.5 AI 晨间简报

显示：

- 生成时间。
- 使用的数据范围与记录数量。
- 1 个核心观察。
- 1～3 个可执行建议。
- “查看完整简报”和“重新生成”。

#### 5.1.6 晚间复盘

复盘表单字段：

- 精力：1～5。
- 情绪：1～5。
- 睡眠质量：1～5。
- 肌肉酸痛或身体不适：1～5。
- 饥饿/饮食满意度：1～5。
- 今日完成感和压力。
- 自由备注。

操作：

- “结束今日并生成复盘”。
- 结束后默认锁定当日计划，但允许重新打开编辑。
- 生成失败时保留状态表单和原始记录。

#### 5.1.7 近 7 天记录

第一版包含：

- 每日计划完成度柱状图。
- 饮水、学习、训练的简要汇总。
- 可切换指标。

#### 5.1.8 两个重要目标倒计时

今日页固定提供两个重要目标倒计时，用于呈现用户当前最关心的两个长期或阶段目标。两个槽位地位相同，均支持自定义标题与目标时间，不自动读取今日计划项。组件应保持克制，不抢占“今日安排”的主视觉，也不使用红色警报、闪烁或惩罚式提醒。

默认配置：

| 槽位 | 类型 | 默认标题 | 行为 |
|---|---|---|---|
| A | 重要目标 | 重要目标 A | 用户填写标题、目标日期和目标时间 |
| B | 重要目标 | 重要目标 B | 用户填写标题、目标日期和目标时间 |

两个槽位相互独立，可分别编辑、启用或停用；任意一个槽位都可以记录考试、项目截止日、阶段目标或其他重要日期。

显示规则：

- 目标超过 1 天：显示“天 + 小时 + 分钟”，例如 `12天 08:32`，每分钟更新。
- 目标在 1 小时至 24 小时之间：显示“时:分:秒”，每秒更新。
- 目标不足 1 小时：显示“分:秒”。
- 目标已到达：显示“已到达”；可同时显示“已过去 N 天”，不显示负数。
- 目标时间使用设备本地时间计算，默认时区为 `Asia/Shanghai`。
- 两个重要目标分别跨日保留，重新进入页面或冷启动后按当前系统时间重新计算。
- 尚未填写目标时显示“添加重要目标”入口；两个槽位都未启用时显示轻量空状态。

交互规则：

- 点击倒计时卡片打开底部抽屉，可修改标题、目标日期时间、备注和启用状态。
- 两个槽位彼此独立，不要求与今日计划或今日记录关联。
- 目标到达后保留原卡片，显示到达状态；用户可以继续编辑、归档或停用。
- 第一版倒计时仅用于展示，不额外发送到点通知；通知能力后续按需增加。
- AI 可以读取倒计时标题和目标时间用于分析，但不能自动修改倒计时。

视觉规则：

- 位置：今日头部与四项指标之后、今日安排之前。
- 桌面端双列并排；手机 390px 以上可双列，360px 使用上下紧凑排列。
- 卡片高度约 96～112px，时间数字使用等宽数字，字号小于页面主标题。
- 两张卡片保持统一的“重要目标”语义，可使用轻微灰蓝差异区分槽位，但不得暗示优先级或警戒等级。
- 使用 `--surface`、`--line` 和 `--accent` 形成轻微强调，不使用高饱和背景。
- 空状态、到期状态和禁用状态必须同时使用文字表达，不能只依赖颜色。

### 5.2 健身

#### 5.2.1 训练计划

支持两种来源：

- 用户手动创建。
- AI 根据档案和历史数据建议，经用户确认后创建。

训练计划字段：

- 名称。
- 训练类型：力量、有氧、柔韧/活动度、综合。
- 计划日期或星期。
- 预计时长。
- 动作列表。
- 备注。

#### 5.2.2 动作与组数

每个动作支持：

- 动作名称。
- 分类或目标肌群。
- 组数。
- 每组次数。
- 重量 kg。
- 时长或距离，用于有氧和计时动作。
- 实际完成组数。
- RPE / 主观强度，可简化为一组全局值。
- 备注。

“数量”必须能表达常见记录方式：

- 3 组 × 12 次 × 20kg。
- 跑步 30 分钟 / 5km。
- 平板支撑 3 组 × 60 秒。

#### 5.2.3 训练记录

- 从今日计划开始训练。
- 支持快速复制最近一次同类型训练。
- 支持暂停、继续和结束训练。
- 完成后的记录进入今日时间线。
- 支持记录未计划但临时完成的训练。

#### 5.2.4 健身统计

第一版：

- 周训练次数。
- 周训练总时长。
- 周总训练容量：重量 × 次数 × 组数。
- 各训练类型占比。
- 最近训练列表。
- 动作重量或次数趋势。

不做：

- 自动动作识别。
- 复杂周期化训练算法。
- 医学意义的疲劳或伤病诊断。

#### 5.5.2 建议字段

基础信息：

- 昵称。
- 年龄段或出生日期。
- 性别，可选。
- 身高、体重，可选。

- 当前学习目标。

- 高数目标。
- 每周可学习时长。
- 常用学习来源。

- 建议语气：直接、温和、简洁。

- 数据发送范围。

#### 5.5.3 建档方式

- 用户确认后保存为档案版本。

### 5.6 AI 分析与建议

#### 5.6.1 AI 任务类型

| 类型 | 输入 | 输出 |
|---|---|---|
| 建档草稿 | 用户填写资料与追问回答 | 结构化档案、待确认项 |
| 晨间简报 | 档案摘要、昨日记录、今日计划、双倒计时 | 核心观察、今日重点、1～3 条建议 |
| 晚间复盘 | 档案、今日计划、双倒计时、记录、状态表单 | 完成情况、关联观察、改进建议 |
| 周报 | 7 天聚合、目标、趋势 | 趋势总结、风险提示、下周建议 |
| 单项解释 | 单个模块统计和用户问题 | 简短解释，不修改正式数据 |

#### 5.6.2 AI 输出结构

建议统一为结构化 JSON：

```json
{
  "summary": "一句话结论",
  "observations": [
    {
      "module": "fitness|diet|water|study|overall",
      "text": "观察内容",
      "evidence": ["数据依据"],
      "confidence": "low|medium|high"
    }
  ],
  "suggestions": [
    {
      "title": "建议标题",
      "detail": "建议内容",
      "actionType": "none|add_plan_item|adjust_target",
      "proposedPayload": {}
    }
  ],
  "questions": ["可选追问"],
  "safetyNotes": []
}
```

规则：

- `actionType` 不为 `none` 时，前端只显示“加入计划/应用建议”按钮。
- 用户确认前，不修改任何正式数据。
- AI 结论必须能对应到输入数据或明确标记为推测。
- 如果记录不足，应直接说明“数据不足”，而不是编造趋势。

#### 5.6.3 AI 调用流程

```text
客户端整理最小上下文
→ 服务端校验身份与请求结构
→ 服务端组合系统提示词
→ 调用 DeepSeek API
→ 解析并校验 JSON
→ 保存报告与输入摘要
→ 返回客户端展示
```

#### 5.6.4 密钥与隐私

- DeepSeek API Key 仅存放在服务器环境变量中。
- 不允许把 Key 编译进 Web 或 Android 包。
- 网络传输必须使用 HTTPS。
- 请求日志不记录完整敏感正文。
- 默认不向 AI 发送照片。
- 用户可查看本次分析使用了哪些数据类别。
- 接入前需阅读 DeepSeek 当前服务条款和隐私政策，并配置关闭不必要的日志留存。

#### 5.6.5 失败与成本控制

- AI 请求超时不影响记录保存。
- 支持超时、限流和 5xx 重试一次。
- 同一数据版本可缓存报告，避免重复扣费。
- 对超长历史只发送聚合数据，不发送全部原始记录。
- 每份报告保存模型名、提示词版本、耗时和 token 使用量。

## 6. 数据模型

### 6.1 设计约定

- 主键使用客户端生成的 UUID，便于离线创建和后续同步。
- 日期字段使用 `YYYY-MM-DD` 的 `dateKey`，并保存实际 ISO 时间戳。
- 所有实体包含 `createdAt`、`updatedAt`。
- 删除使用软删除 `deletedAt`，便于撤销和同步。
- 数值单位固定：ml、kg、cm、分钟、kcal、克。
- JSON 扩展字段必须带版本，避免未来结构失控。
- 聚合数据实时计算，除非是 AI 报告快照。

### 6.2 核心实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Profile | id, displayName, birthDate, sex, heightCm, weightKg, goals, constraints, preferences, updatedAt | 个人档案 |
| ProfileVersion | id, profileId, snapshotJson, reason, createdAt | 档案版本 |
| DailyPlan | id, dateKey, state, userNote, source, createdAt | 每日计划 |
| PlanItem | id, dailyPlanId, module, title, plannedAt, durationMin, status, linkedRecordId | 计划项 |
| Countdown | id, slot, title, targetAt, note, enabled, createdAt, updatedAt | 今日两个重要目标倒计时，最多两条 |
| DailyCheckIn | id, dateKey, energy, mood, sleepQuality, soreness, stress, note | 晚间状态 |
| FitnessSession | id, dateKey, planItemId, type, startedAt, durationMin, rpe, note, status | 一次训练 |
| ExerciseEntry | id, sessionId, name, category, order, note | 训练动作 |
| ExerciseSet | id, exerciseEntryId, setNo, reps, weightKg, durationSec, distanceM, completed | 单组明细 |
| Meal | id, dateKey, mealType, eatenAt, title, caloriesKcal, proteinG, carbsG, fatG, photoRef, source, note | 餐次记录 |
| WaterRecord | id, occurredAt, amountMl, recordType, note, deletedAt | 饮水记录 |
| StudySession | id, dateKey, category, source, startedAt, durationMin, newCount, reviewCount, questionCount, correctCount, note | 学习记录 |
| AiReport | id, kind, dateKey, rangeStart, rangeEnd, model, promptVersion, inputSummary, resultJson, status, createdAt | AI 报告 |
| ReminderSetting | id, type, enabled, times, weekdays, lastTriggeredAt | 提醒设置 |
| AppSetting | key, valueJson, updatedAt | 应用设置 |
| SyncOutbox | id, entityType, entityId, operation, payloadJson, retryCount, createdAt | 可选同步队列 |

### 6.3 聚合规则

- 饮水合计按 `deletedAt = null` 的 `amountMl` 求和。
- 饮食合计按餐次热量和营养字段求和。
- 学习合计按 `durationMin` 求和，英语与高数分别汇总。
- 训练次数按已结束的训练会话计数。
- 训练容量按每组 `reps × weightKg` 求和，无重量的动作不计入容量。
- 计划完成率按已完成计划项 ÷ 总计划项计算，跳过项默认不算完成，但单独统计。
- 日期边界按用户设置的本地时区计算，默认 Asia/Shanghai。
- 两个重要目标倒计时均按 `targetAt` 持久化并实时计算；目标时间已过时显示已到达状态，不生成负数倒计时。

- Local Notifications。
- Filesystem / Share。
- 加密存储用于设备端服务令牌，不保存 DeepSeek Key。

#### 服务端

- Node.js + TypeScript + Fastify。
- SQLite + Drizzle ORM。
- DeepSeek API 代理。
- 请求校验、限流、日志脱敏。
- Docker Compose 部署。
- Caddy 或 Nginx 提供 HTTPS。

### 7.2 前端分层

```text
pages          页面与路由
features       今日、健身、饮食、学习、AI、档案
components     通用 UI 组件
domain         聚合、单位、日期、业务校验
db             Dexie 表、迁移、仓储
services       AI、导出、导入、提醒、同步
stores         UI 与少量会话状态
```

约束：

- 页面不直接操作 Dexie 表，通过仓储或领域服务。
- 热量、饮水和时长聚合要有单元测试。
- 组件只接收领域对象，不感知数据库结构。
- AI 响应先经 Zod 校验再进入界面。

### 7.3 本地数据与迁移

- Dexie 数据库包含 `version` 和升级函数。
- 任何正式发布后的表结构修改都必须提供迁移。
- 首次启动创建默认设置和目标空值。
- 数据导入先校验版本，再执行事务式合并。
- 备份文件包含 schemaVersion、exportedAt、appVersion 和实体数组。

### 7.4 服务端职责与阶段

#### MVP 阶段

- DeepSeek API 代理。
- 健康检查。
- 单用户访问令牌。
- 手动备份上传与恢复。
- 请求日志脱敏。

#### 后续阶段

- 增量备份。
- 多设备同步。
- 冲突展示与人工选择。
- 备份完整性检查和定时任务。

不建议在 MVP 一开始就实现复杂双向同步。先确保本地数据模型、导出和恢复可靠，再扩展同步。

### 7.5 同步预留设计

- 客户端生成 UUID。
- 每条记录带 `updatedAt`、`deletedAt`、`serverRevision`。
- 本地维护 Outbox。
- 首次同步可先做“设备快照上传”和“另一设备整库拉取”。
- 真正的多设备合并延期到后MVP阶段。

## 10. GitHub 开源项目参考计划

在第一阶段工程初始化前，应完成一次开源项目调研。调研目标不是直接拼装项目，而是借鉴数据模型、交互和统计方式。采用任何代码前必须核查 License、维护状态和依赖安全。

| 模块 | 候选参考 | 重点观察 | 采用方式 |
|---|---|---|---|
| 健身 | wger、FitTrackee、其他开放训练记录项目 | 动作、组数、重量、训练计划数据模型 | 借鉴模型与交互，不直接复制受限代码 |
| 饮食 | Open Food Facts、OpenNutriTracker 等 | 餐次、热量、宏量营养素、照片附件 | 第一版不导入完整食物库 |
| 饮水 | 旧 Water intake record + 开源饮水应用 | 快捷容量、撤销、目标、7 天趋势、提醒 | 以旧工具行为为产品基线 |
| 学习 | Anki 及开源学习统计项目 | 学习会话、数量、复习统计、图表 | 第一版只借鉴统计维度 |
| AI | DeepSeek 官方示例与 SDK 文档 | 请求格式、流式输出、错误码、成本 | 使用官方接口与自建代理 |

调研输出要求：

- 每个模块至少比较 2 个候选项目。
- 记录 License、技术栈、数据结构和可借鉴点。
- 明确“借鉴、重写、放弃”的结论。
- 不在未确认 License 的情况下复制代码。
- 不引入会破坏本地优先和隐私原则的第三方追踪 SDK。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围持续扩张 | MVP 延期 | 严格执行必做/暂缓清单，新功能进入 Backlog |
| 饮食照片识别复杂 | 阻塞饮食模块 | 第一版只做手动录入和可选附件 |
| AI 建议不准确 | 误导用户 | 展示依据、置信度，强制用户确认 |
| DeepSeek 服务不可用 | AI 功能不可用 | 本地功能独立，错误提示和缓存结果 |
| API Key 泄露 | 费用和安全风险 | 仅服务端保存，禁止进入客户端包 |
| 本地数据丢失 | 长期记录受损 | 自动备份、JSON 导出、恢复演练 |
| 多设备同步冲突 | 数据覆盖 | MVP 不启用双向同步，先做备份 |
| Android 与浏览器差异 | 页面或权限异常 | 尽早真机测试，统一能力适配层 |
| 数据库迁移失败 | 升级后打不开 | 迁移测试、事务、升级前自动备份 |
| 设计漂移 | 页面风格不统一 | 使用固定 Token 和共享组件 |
| 过度记录负担 | 用户放弃使用 | 快捷记录、可空字段、默认值、撤销 |
| 医学/营养建议边界 | 安全风险 | 明确非医疗建议，异常情况提示专业帮助 |
| 倒计时制造持续压力 | 使用焦虑、回避打开应用 | 仅保留两个槽位，不使用红色闪烁和惩罚式提醒 |

## 附录 B：术语

- **今日闭环**：计划、记录、聚合、复盘形成完整一天。
- **本地优先**：所有核心写入先落本地数据库，服务器不可用时不影响使用。
- **结构化 AI 输出**：使用固定 JSON schema 返回观察和建议，便于校验与确认。
- **确认式修改**：AI 不能直接写数据，必须由用户点击确认。
- **软删除**：记录保留删除时间，便于撤销、备份和未来同步。
- **Outbox**：本地待同步操作队列。
- **视觉 Token**：颜色、间距、圆角、阴影等统一设计变量。
